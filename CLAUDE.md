# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A static multi-page site for **Backroom Brewery** (Middletown, VA) — `backroombreweryva.com`. All site content lives in `web/`. Each page is a **self-contained single HTML file** (markup + inline `<style>` + inline `<script>`):

- `web/index.html` — **the live multi-page home** (promoted from the old `home.html` in Aug 2026): hero, mission, awards band, and an "explore" grid that acts as the site map linking to every subpage. Uses **relative** asset paths (unlike subpages).
- `web/index-backup.html` — the retired legacy single-page site (hero, story, taproom, events, visit, signup all on one page with anchor nav), kept as a backup. It still deploys to the bucket (reachable at `/index-backup.html`); its canonical points to `/`, so it won't compete in search. Not linked from anywhere.
- `web/story/index.html` (`/story`) — mission + origin story + timeline + awards. Nav label: "Our Story" under About.
- `web/farm/index.html` (`/farm`) — what's growing on the farm: hops in the hop yard (first planted 2012), sweet + red basil, roma tomatoes in the high tunnel, plus a "Field Notes" photo gallery (`/images/farm/`, masonry via CSS columns) and a beds-to-brewhouse card noting basil, red basil, and lemon zest go into the beers. Update seasonally. Nav label: "The Farm" under About.
- `web/taproom/index.html` (`/taproom`) — taproom cards + farm feature band. Not in the nav menus; reachable from the home explore grid and cross-links.
- `web/beers/index.html` (`/beers`) — draft beer tap list: the real 31-recipe lineup (names/styles/ABVs/IBUs from the brewery's beer list, Aug 2026). High-alcohol beers note they're served in half pints; seasonal beers carry availability in their style line. Carries a **21+ age gate** (simple "Are you over 21?" yes/no modal at the top of `<body>` — not a legal requirement; owner chose yes/no over the Brewers Association code's preferred birthdate entry) that remembers verification in `localStorage` (`brbAgeVerified`); it's this page only, by choice.
- `web/food/index.html` (`/food`) — the real kitchen menu (from the taproom menu board, Aug 2026): sandwiches served with 2 sides, snacks & shareables (priced dotted-leader lists), and a sides card (pill list) + "beyond the taps" beverages (wine, cider, zero-proof). Update when the menu board changes.
- `web/events/index.html` (`/events`) — "Don't Miss": a **hand-maintained static event list** (month-grouped cards) with matching `Event` JSON-LD in the `<head>` — **update both together** when events change. Each `Event` carries the Google-recommended `description`/`url`/`image`/`organizer` props — keep them when adding events; `offers` is deliberately absent until free admission is confirmed with the owner. The Facebook Graph feed (`GET /prod/fbevents` via `/config.json`) was removed from this page until the token pipeline is functional; the fbevents Lambda still deploys, and the fetch/render code can be restored from git history.
- `web/private-events/index.html` (`/private-events`) — the Big Barn venue page (rehearsal dinners, corporate retreats, birthdays/private parties, capacity badge, inquiry CTAs), split out of the old combined `/events` page. Retargeted away from wedding keywords (Aug 2026) so it doesn't cannibalize `/weddings`: title/meta/OG lead with private events, the featured package reads "Full-Day Buyout" here vs "Full Wedding Day" on `/weddings`, and the pricing note cross-links weddings. Includes the **Golden Acre Events** amenity list, three rental packages (Mezzanine $250/hr; Shenandoah Sunset "starting at $1,500, up to $4,500"; Shenandoah Golden Acre "starting at $3,000, up to $9,000"), and booking terms — prices from the "Golden Acre Events Venue Pricing Booklet" PDF (Aug 2026). Pricing is deliberately shown as starting-at + peak range (the booklet's full season×day tables were summarized away, Aug 2026); the JSON-LD `makesOffer` min/max prices must stay in sync when pricing changes. Package prices are also repeated on `/weddings` — update both pages together.
- `web/weddings/index.html` (`/weddings`) — wedding-dedicated landing page split off the private-events content (Aug 2026): ceremony/reception/getting-ready cards, wedding photo gallery, Golden Acre amenity list, and the two wedding packages (Shenandoah Sunset, Shenandoah Golden Acre — same prices as `/private-events`, keep in sync; the Mezzanine is mentioned in the pricing note with a link to `/private-events`). JSON-LD is a `BreadcrumbList` plus a `WebPage` whose `about` points at the `/private-events#bigbarn` entity — venue facts/offers deliberately live only in the `/private-events` schema to avoid double maintenance. Nav label: "Weddings" under Events.
- `web/visit/index.html` (`/visit`) — hours table + address/directions. Nav label: "Visit Us" under Contact.
- `web/connect/index.html` (`/connect`) — the ALTCHA-gated signup form (the only nav page that loads the ALTCHA CDN script). Nav label: "Stay In Touch" under Contact.
- `web/faq/index.html` (`/faq`) — styled `<details>` FAQ accordion, 14 Q&As mirrored in the `FAQPage` schema (keep both in sync). **Drafted answers** marked with HTML comments — review hours/reservation policy before promoting; the beer-to-go and wheelchair-accessibility items are individually flagged pending owner confirmation.
- `web/holidaymarket/index.html` (`/holidaymarket`) — vendor page, intentionally not linked from the nav.
- `web/404.html` — branded not-found page (`noindex`), linked from nowhere and absent from the sitemap. It only actually serves for bad URLs once the distribution's Custom Error Response (403 → `/404.html`, response code 404) is configured — see the `cloudfront` notes in `iac/config/common.yml`.

There is **no build system, package manager, bundler, framework, or test suite**. The HTML files are the deploy artifact.

**Google Analytics 4 is on every page.** Each HTML file (all 15, including `index-backup.html`, `holidaymarket`, and `404.html`) carries the gtag.js snippet (measurement ID `G-J0Z6SHHTDQ`) right after the viewport meta in `<head>`. Add it to any new page. Conversion events: `sign_up` fires on the `/connect` signup success, `generate_lead` on the holidaymarket vendor-form success and on `/private-events` and `/weddings` mailto clicks.

**Shared chrome is duplicated by design.** The nav (with mobile hamburger menu), page-hero, footer, brand tokens, buttons, and reveal CSS/JS are copy-pasted into every page — when editing shared chrome, update **all pages** to keep them in sync. Subpage nav is always solid; the home nav is transparent until scrolled (`.scrolled`). Subpages use **absolute** asset paths (`/images/...`, `/config.json`); the home page uses relative paths.

**Nav structure (new site) is a dropdown menu system:** Food & Drinks → `/beers`, `/food` · About → `/story` (Our Story), `/farm` (The Farm) · Events → `/events` (Don't Miss), `/private-events`, `/weddings` (Weddings) · Contact → `/connect` (Stay In Touch), `/faq`, `/visit` (Visit Us). Desktop shows hover/click dropdown panels (`.nav-item` / `.nav-drop`, plus a `@media (min-width: 961px)` block); mobile renders them as an accordion inside the hamburger panel (`.nav-item.open`). The current page's link gets `class="active"` + `aria-current="page"`, **and** its parent dropdown toggle gets `class="active"`. The dropdown markup/CSS/JS is identical on every page — changing the menu means updating all 12 pages.

## Running locally

Serve the `web/` directory:

```sh
cd web && python3 -m http.server 8000   # then visit http://localhost:8000
```

## Architecture notes worth knowing before editing

- **Single-file pages by design.** Don't extract CSS/JS into separate files or introduce a build step unless explicitly asked — the deploy model is "upload these standalone HTML files."
- **Brand palette and typography live in CSS custom properties** at `:root` (`--ink`, `--paper`, `--bronze`, `--barn`, `--wood`, `--display`, `--body`). Reuse these tokens rather than hardcoding colors/fonts. Fraunces (display) and Newsreader (body) are loaded from Google Fonts.
- **SEO is heavy and intentional.** The home `<head>` has primary meta, Open Graph, Twitter Card, geo tags, and a JSON-LD `@graph` declaring the business as `Brewery / Restaurant / EventVenue / LocalBusiness` plus a `SiteNavigationElement` listing the subpages. Subpages carry lighter meta (title, description, canonical, OG) **plus a `BreadcrumbList` JSON-LD**; `/faq` also has `FAQPage` schema (must mirror the visible Q&As) and `/private-events` has an `EventVenue`/`LocalBusiness` schema targeting wedding + corporate-event searches. Hiker/outdoors phrasing (Skyline Drive, Shenandoah National Park, Appalachian Trail) is worked into `/beers`, `/food`, `/taproom`, `/visit`, and the FAQ. `web/robots.txt` and `web/sitemap.xml` are deployed as real bucket keys (no alias needed); **the sitemap lists the pretty URLs and must be updated when pages are added/removed**. When changing address, hours, phone, or branding copy, update **all** of: visible text on every affected page, meta description/keywords, OG tags, and the JSON-LD blocks — these must stay in sync. Hours appear in four places: home hero `.hours-bar`, `/visit` hours table, the FAQ (text + FAQPage schema), and the home JSON-LD. **Canonical-domain caveat**: all canonicals, JSON-LD, and the sitemap use `https://www.backroombrewery.com` — if the site actually serves at a different domain (e.g. `backroombreweryva.com`), find-and-replace across every page + sitemap + robots before launch.
- **Reveal animations** are driven by an `IntersectionObserver` at the bottom of the file that adds `.visible` to elements with class `reveal`. Add `reveal` (plus `delay-1`…`delay-4`) to new elements you want to fade in.
- **Signup form** (`#signupForm` in `web/connect/index.html`) POSTs JSON to the URL in its `action` attribute, which is set at load from `/config.json` (`signupUrl`). The form includes a `_gotcha` honeypot field; don't remove it.
- **ALTCHA captcha gates the submit button.** The `<altcha-widget>` (loaded from jsdelivr CDN) fetches a signed challenge from `challengeurl` (set at load from `/config.json`'s `altchaChallengeUrl`) and computes a proof-of-work. The "Notify Me…" button is hidden via CSS until the widget fires `statechange` with `state === 'verified'`, at which point the form gets a `.altcha-verified` class. `handleSignup` also short-circuits if the class is missing (so Enter-key submissions can't bypass it). The widget injects a hidden `altcha` field into the form payload that the signup Lambda re-verifies server-side.
- **The live site is CloudFront with the bucket's S3 REST endpoint as origin** — there is **no directory-index behavior**. Only the root gets `index.html` (CloudFront default root object); `/somepage` does NOT serve `somepage/index.html`. Subdirectory pages need an alias object at the bare key — see `SiteAliasObjects` in the infra section.
- **Holiday Market vendor page** at `web/holidaymarket/index.html` (served as `/holidaymarket`, intentionally **not linked from the main page**). Same conventions as the main page: single file, inline CSS/JS, brand tokens, `_gotcha` honeypot, ALTCHA-gated submit, and `/config.json` at load (uses `holidayMarketUrl` + `altchaChallengeUrl`; posts JSON to `POST /prod/holidaymarket`). Asset paths on this page are **absolute** (`/images/...`, `/config.json`) because it lives in a subdirectory. Photos are collected as **links** (textarea), not uploads — API Gateway/SES payload limits make real uploads impractical for this pipeline.

## Infrastructure (`iac/`)

Python AWS CDK app that uploads the static site to a **pre-existing** S3 bucket and deploys the signup Lambda. Each AWS resource lives in its own file under `iac/stacks/resources/`.

- **Config is layered YAML.** `iac/config/common.yml` holds shared defaults; `iac/config/<env>.yml` (e.g. `dev.yml`) holds per-env overrides and is deep-merged on top. Pick env via `BRB_ENV` (default `dev`). The bucket is **referenced by name from config** (`existingBucketName`) — the stack does not create or own it.
- **Tagging + naming convention** lives in `iac/stacks/naming.py` as the `Naming` class. Pattern is `<prefix>-<core>-<suffix>` where `prefix` defaults to `project` and `suffix` defaults to `env` (both can be overridden in config). The "core" is **owned by each resource construct** as a class-level `CORE_NAME` constant (e.g. `SignupFunction.CORE_NAME = "signup-lambda"`, `SiteStack.CORE_NAME = "static-site"`) — there are **no resource names in config**. `naming.apply_default_tags(self)` is called once on the stack, and CDK's tag aspect propagates `project` + `env` tags to every taggable resource inside. **Exception**: `existingBucketName` is the literal name of an external bucket — it doesn't follow this convention.
- **`SiteDeployment` runs with `prune=False`** because the bucket is shared/pre-existing — never let it delete objects it didn't put there. The upload is split in two so each content class carries an explicit Cache-Control: images `public, max-age=2592000` (30 days), pages/text `public, max-age=300, must-revalidate` (5 min). Set `cloudfront.distributionId` in `<env>.yml` and every deploy also issues a `/*` edge invalidation.
- **`SiteAliasObjects`** (`iac/stacks/resources/site_alias_objects.py`) re-uploads subdirectory pages at their bare key (e.g. key `holidaymarket` = copy of `holidaymarket/index.html`, content-type text/html) so pretty URLs work through the CloudFront + S3-REST-origin setup. Add new subdirectory pages to its `aliases` map in `site_stack.py`. The trailing-slash variant (`/holidaymarket/`) is served by a **manually uploaded** object with the literal key `holidaymarket/` (S3 allows slash-suffixed keys; BucketDeployment can't create them) — re-upload it via `aws s3api put-object` if the page changes materially, or better: delete it once EdgeRedirects is attached (below). Alias objects carry the same 5-min HTML Cache-Control as SiteDeployment.
- **`EdgeRedirects`** (`iac/stacks/resources/edge_redirects.py`, code in `iac/cloudfront/redirects.js`) is a CloudFront Function that 301s apex→www and strips trailing slashes (`/beers/` → `/beers`). Deploys only create/publish the function; **attaching it as the default behavior's viewer-request function is a one-time manual step** (the distribution is not managed by this stack — its ARN is in the `EdgeRedirectsFunctionArn` output). Once attached, delete the manual `holidaymarket/` slash object and the trailing-slash 403s are gone for every page.
- **`SignupFunction`** code lives at `lambda/signup/handler.py` (project root, **not** under `iac/`). Path is set in `iac/config/common.yml` as `lambda.codePath` (relative to project root). The CDK stack does not create API Gateway; wire that separately when ready, then update the form `action` in `web/index.html` (currently a `YOUR-API-GATEWAY-URL...` placeholder).
- **`AltchaChallengeFunction`** at `lambda/altcha-challenge/handler.py` issues HMAC-signed ALTCHA proof-of-work challenges for the captcha widget. Both this Lambda and the signup Lambda share an HMAC secret resolved at synth in this order: `ALTCHA_HMAC_KEY` env var → `altcha.hmacKey` in config → auto-generated and cached at `iac/.altcha-hmac-key` (gitignored). For prod/CI, **always set `ALTCHA_HMAC_KEY`** so the key is reproducible across machines; the on-disk cache is a single-developer convenience only.
- **`HolidayMarketFunction`** at `lambda/holidaymarket/handler.py` (`CORE_NAME = "holidaymarket-lambda"`) backs the `/holidaymarket` vendor application form. Same ALTCHA verification + honeypot as the signup Lambda; emails each application via SES with subject `BRB Holidaymarket Signup - <contact name>` and Reply-To set to the applicant. Recipient defaults to `ses.toAddress`; override with `holidayMarket.toAddress` in config (the override is auto-added to the SES verify list). Lambda settings live under `holidayMarket.lambda` in `common.yml`.
- **`FacebookEventsFunction`** at `lambda/fbevents/handler.py` (`CORE_NAME = "fbevents-lambda"`) proxies the Facebook Graph API `/{page-id}/events` edge for the `/events` page, keeping the Page access token server-side. Config lives under `facebook.*` in `common.yml` (`pageId`, `graphVersion`, `cacheSeconds`, `eventsLimit`). The token resolves at synth as `FB_PAGE_TOKEN` env var → `facebook.pageToken` in config; **never commit a real token** — without one the endpoint returns `{configured: false, events: []}` and the page shows only the Facebook fallback link. Responses are cached in the warm container **and** via `Cache-Control: public, max-age=<cacheSeconds>`; Graph API failures serve stale cache when available. Getting a token: create a Meta app (dev mode is fine), grant it the page via Graph API Explorer, exchange a long-lived user token for a Page token.
- **`SiteApi`** (`iac/stacks/resources/api.py`) is a REST API Gateway that fronts the Lambdas at `GET /prod/altcha`, `GET /prod/fbevents`, `POST /prod/signup`, and `POST /prod/holidaymarket` with CORS preflight handled by API Gateway itself. The URLs are also emitted as CFN outputs (`ApiBaseUrl`, `AltchaChallengeUrl`, `SignupUrl`, `HolidayMarketUrl`, `FbEventsUrl`) — useful for debugging but **not** required for the page to work. CORS allowlist is configurable via `api.allowedOrigins` (defaults to any origin).
- **`SiteRuntimeConfig`** (`iac/stacks/resources/site_runtime_config.py`) writes a `/config.json` to the site bucket using `Source.json_data(...)` with keys `apiBaseUrl`, `altchaChallengeUrl`, `signupUrl`, `holidayMarketUrl`, `fbEventsUrl`. CDK substitutes the API URL tokens at deploy time; each static page fetches `/config.json` on load and sets its form endpoint + `<altcha-widget challengeurl>`. This means the HTML doesn't need to be regenerated when the API id changes — **a single `cdk deploy` produces a working page**. Cache-Control is `no-store` so the file is never cached.
- **`SiteDeployment` source path** is `../web` (relative to `iac/`), set in `iac/config/common.yml` as `siteSourcePath`. Only `web/` gets uploaded — repo metadata, IaC, and docs are not part of the deploy bundle.
- **Deploy:** `cd iac && python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt && cdk deploy` (requires AWS credentials and `cdk bootstrap` in the target account/region).
